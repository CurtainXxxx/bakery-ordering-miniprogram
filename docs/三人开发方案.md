## 4. 目标业务与功能清单

场景边界：一家烘焙门店，顾客选购预订、配送或自取，店员履约，店主维护商品库存、管理人员和处理售后。商品预订以可售数量为约束，暂不做生产排程与时段容量。

|---|---|---|---|

| FR-02 | 商品检索与商品管理 | 分类、关键字检索、分页、上下架、有效价格及商品图；下架商品不能下单 | B |

## 5. 关键设计决策

### 5.1 分层与模块

采用小程序页面 → 客户端 API 封装 → 云函数入口与认证 → 业务服务 → 数据访问的分层结构。保持简单部署，初期可以一个业务 API 云函数配独立超时任务，业务模块按文件拆分，避免分散云函数之间共享代码打包不一致。

建议至少实现七个可对应到详细设计图的服务类：AuthService、CatalogService、OrderService、InventoryService、FulfillmentService、AfterSaleService、StatisticsService。补 AddressService、NotificationService 视实现需要。类图必须反映真实职责与调用关系，不为了凑“五个类”画空壳。

接口约定使用显式业务动作，例如 createOrder、simulatePay、cancelOrder、shipOrder、completePickup、applyAfterSale、reviewAfterSale。避免一个无约束的 updateOrder 接口。统一返回业务错误码，例如 FORBIDDEN、OUT_OF_STOCK、INVALID_STATE、PRICE_CHANGED，前端按错误码显示可操作的提示。

### 5.2 可信金额、库存与重复请求

- 所有金额采用整数“分”，最终金额由服务端根据商品、数量、配送方式和运费规则计算。地址从用户拥有的地址记录读取并形成订单快照。
- 下单保存商品名称、单价、数量、地址、运费规则版本等快照，后来改价不能改变旧订单。
- 库存定义 onHand（在库）、reserved（预留）、available=onHand-reserved；始终满足 0≤reserved≤onHand。
- 创建待支付订单：事务校验可售数量，增加 reserved，并保存订单、请求标识和业务日志。相同用户与 requestId 的重试返回原订单；相同标识但不同参数应拒绝。
- 模拟支付成功：事务中检查未过期和状态，onHand、reserved 同时减去购买数量，并记录支付结果。
- 未支付取消或超时：只减少 reserved。取消、超时、支付发生竞争时，仅一个合法转换可以提交。
- 售后退款与库存退回分开定义。烘焙商品已发货后的退款不自动增加可售库存；未履约订单是否恢复库存由明确规则决定，并且只执行一次。
- 通知在事务提交后处理；事务重试过程中不能发送外部消息。先实现站内业务记录，机器人作为可配置通知通道，测试默认不联系实际商家。

上述是期望语义。第一阶段应在实际 SDK 和云环境中做事务能力验证，检查原子提交、冲突重试与请求去重方案，再确定代码实现，不能把内存模拟测试当成事务验证。

### 5.3 订单与售后状态

主订单：待支付 → 待接单 → 已接单 → 配送中／待自取 → 已完成；待支付可转已取消或已超时。模拟支付失败保持待支付。每次转移检查角色、当前状态和必要字段，并原子写入事件。

售后单独建模：已申请 → 已批准／已拒绝 → 模拟退款完成。首版只做整单退款：未履约订单允许取消退款；配送中或已完成订单允许提出售后，但是否退款由店主审核。申请售后不应直接覆盖订单主状态；审核与履约竞争时重新检查状态，再确定能否退款、是否停止履约、是否恢复库存。

商家可拒单并执行整单模拟退款，需要记录拒单原因。顾客不能通过重复请求或修改订单 ID 影响其他人订单。

### 5.4 认证与数据访问

顾客使用微信身份，角色以服务端用户记录为准。首次店主由受控初始化步骤绑定，禁止用户自行传 role 升级。

为覆盖模板明确写出的“口令加密存储”，默认保留员工后台二次口令：服务端采用成熟的加盐口令哈希方案，限制失败重试，建立有过期时间且绑定当前微信身份的服务端会话；所有员工操作校验会话与角色。哈希记录禁止客户端读取。实现中不使用明文、可逆加密或单次无盐摘要代替口令哈希。若教师明确接受纯微信免密码认证，可取消该额外模块并记录适用说明，不能自行认定免做。

商品库存、订单、角色、支付与售后由服务端写入，客户端直接写入应被拒绝；公开商品读取与个人地址访问按用途配置规则，导出规则与索引并纳入部署说明。数据库规则之外，云函数本身仍执行授权与归属校验。数据库权限配置参考 [CloudBase 安全规则](https://docs.cloudbase.net/database/security-rules)。

### 5.5 数据结构

保留并规范 products、carts、addresses、orders、shop_config；课程版不依赖真实收款码，可停用 payment_config。

新增 users（身份/角色/defaultAddressId）、staff_credentials 与 staff_sessions（后台认证）、payments（模拟支付/退款记录）、order_events（状态与操作历史）、inventory_movements（库存流水）、after_sales（售后）。重复请求标识可嵌入原子订单创建方案，或设独立 request_keys 集合，不能仅靠客户端去重。

orders 重点字段：ownerOpenid、items 快照、amounts 整数分、deliveryType、addressSnapshot、status、paymentStatus、expiresAt、createdAt、version、requestId。索引围绕“用户+时间”“状态+时间”“待支付+到期时间”“售后所属订单”设计，在目标数据库中验证具体组合。

统计口径：成交额取模拟支付成功金额，退款额取模拟退款成功金额，净额=成交额-退款额；商品销量取完成订单的有效数量，并说明整单退款处理方式。未支付、失败、取消金额不计作成交收入。页面明确标记测试经营数据。

1. 每人同时负责模块代码、模块测试和模块文档，C 负责汇总质量材料，不承担另外两人的全部测试。
2. B 不直接修改库存扣减逻辑；商品库存调整页面调用 A 的接口。C 不在自己的页面或服务中随意改订单状态，使用 A 定义的状态转换和退款原子操作。
3. 公共入口、鉴权、状态枚举、金额规则和接口文档由 A 维护；B/C 通过需求或合并请求修改公共约定。各自维护独立模块文件。
4. 将现在集中在 admin.js 的商品管理、履约、售后、统计拆成独立页面。B 维护商品和店铺页面，C 维护履约、售后和统计页面，避免三个人反复修改同一个大文件。
5. A 负责集成不等于代写所有未完成任务。每个里程碑必须看到三个人各自可验收的提交；任务未完成时先削减 P2 和视觉润色，不能删掉硬性要求。
6. 贡献度在结束时按真实代码、设计、测试、集成与文档工作确定，不预填固定 1/3，也不只按提交次数计算。

## 7. 推荐目录与 Git 协作

建议从原源码建立独立正式开发目录，例如 `D:\软件工程作业\小程序\开发版`，首个提交注明“导入既有项目基线”。本方案描述后续迭代目标；当前仓库是经敏感配置清理的既有项目基线。

```text
开发版/
  src/
    miniprogram/             页面、组件、客户端 API 封装
    cloudfunctions/
      api/                  入口、auth、services、repositories
      expireOrders/         调度入口，调用统一超时规则
  docs/                     需求、接口、UML、会议与看板记录
  test/                     单元、集成、流程、性能用例和结果
  scripts/                  测试数据、配置校验、打包与统计脚本
  project.config.json       miniprogramRoot/cloudfunctionRoot 对应新目录
  README.md
```

Git 采用 main + 短期 feature 分支；A/B/C 分别按模块开发，完成一个小功能就提交。每天开始先同步，合并前运行相关测试，由另一人检查。三人各用自己的身份提交，禁止最后一天由组长代替所有人上传全部代码。

头歌是正式交付仓库。GitHub 可以用于协作，但应按里程碑同步到头歌并验证三人提交历史和访问权限。看板至少包含待做、开发中、待验收、已完成；每次例会记录日期、参与人、决定及阻塞事项。

## 9. 冲击 95+ 的验收标准

### 9.1 必须演示的业务和异常

| 场景 | 期望结果 |
|---|---|
| 正常订单 | 顾客下单模拟支付，店员接单履约，顾客看到完整状态记录 |
| 改低客户端金额 | 服务端采用可信价格或明确拒绝，不能生成低价订单 |
| 同一请求重复提交十次 | 只产生一个业务订单，库存只预留一次 |
| 五件库存、二十个独立用户同时购买一件 | 至多五个成功，剩余明确库存不足，库存不负数且账目一致 |
| 支付与超时、取消竞争 | 只发生一个合法结果，不出现既支付又释放库存 |
| 顾客访问他人订单、店员调价或退款 | 服务端拒绝；数据库直写同样不可绕过 |
| 模拟支付失败与重试 | 失败不扣实物库存，成功只执行一次；取消和超时按规则释放 |
| 默认地址被修改 | 只存在一个有效默认指向，不能选用其他用户地址 |
| 售后重复审核、退款失败重试 | 不重复退款，订单/售后/支付记录一致 |
| 通知失败 | 订单保持成功，日志可定位失败，不因通知失败生成第二笔订单 |
| 统计对账 | 测试数据包含未支付、取消、完成、退款订单；统计与手算预期一致 |

单元测试覆盖计价、运费边界、权限策略、状态转换；集成测试覆盖真实数据库事务与权限；确认测试覆盖三角色完整流程。每条测试含 TC 编号、FR/NFR、前置数据、步骤、预期、实际及结论。发现问题登记缺陷并保留修复前后证据。

### 9.2 性能与质量门槛

- 核心查询选定商品列表、本人订单列表、履约订单列表，使用固定数据集，例如 200 个商品和 2000 笔订单，并说明页大小和筛选条件。
- 50 个并发用户需有各自的逻辑会话/数据范围和持续请求，不把一次 Promise.all 的 50 个调用直接当成通过证明。
- 记录持续时间、请求量、成功率、平均值、P95、最大值、冷启动与网络条件。课程底线是核心查询不超过 2 秒，不能只报告平均值或 P95 而隐去超过 2 秒的样本；超限要记录原因并优化重测。
- 事务并发正确性和响应时间分开验收，快速返回错误不等于系统达到业务并发能力。
- 压测只在独立测试环境执行，先验证云资源配额和费用边界。尚未完成压测时，报告写“待验证”，不填假数据。
- 以核心流程全部通过、已知严重缺陷为零为交付门槛；最终测试通过率至少满足模板的 95%，剩余失败必须解释影响，不能把核心失败藏在总体比例内。

### 9.3 七个评分维度的准备重点

| 维度 | 权重 | 95+ 目标下需要拿出的材料 |
|---|---|---|
| 背景与调研 | 5% | 真实商家访谈与原作者使用经历，2～3 款同类产品的具体证据与对比；不编造运营成效 |
| 需求 | 15% | FR/NFR 编号、三角色、至少五个用例规约、异常和边界规则、可追溯测试 |
| 设计 | 25% | 分层与部署图、界面原型/导航、分析类图、设计类图、顺序图、活动图、状态图、完整数据字典和索引理由 |
| 编码 | 20% | 核心规则正确、模块职责清晰、代码量口径真实、持续提交、AI 与复用说明、头歌可访问 |
| 测试 | 20% | 全部需求覆盖、真实缺陷闭环、并发与性能证据、完整且有解说的视频 |
| 部署与总结 | 10% | 固定依赖、配置示例、种子数据、角色初始化、权限规则、从零部署复现、日志/备份说明、每人反思 |
| 协作 | 5% | 三人有真实开发成果、看板与会议记录、里程碑和提交分布；报告分工与实际相符 |

优先选择能同时形成“规则、代码、设计图、异常测试、演示”的改进。订单事务和售后状态管理比额外增加装饰性页面更值得投入，但界面仍须清晰、稳定、没有阻断操作的错误。
